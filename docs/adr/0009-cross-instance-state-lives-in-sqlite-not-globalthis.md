# Cross-instance mutable state lives in SQLite by default; `globalThis` is reserved for wiring that can't be serialized, and a lint rule guards the boundary

Next.js's standalone build gives `instrumentation.node.ts` and each route handler a separate module instance of any file they both import, so a plain module-level `let` set by one is invisible to the other. This has now broken production twice from the same root cause: #91 found `src/lib/ollama/client.ts`'s `modelCallRecorder` silently unrecorded when Ollama was called from a route rather than boot, and #92 found the Planner's `runInFlight`/`running` guard in `src/lib/planner/planner.ts` never actually blocking overlapping runs. #91 fixed its case with a `globalThis` slot keyed by `Symbol.for(...)`, but that fix being merged and documented didn't stop #92 — a second, structurally identical `let` shipped in a different file regardless.

For #92 we chose SQLite over repeating the `globalThis` pattern: `runInFlight` and `running` are genuinely *data* — facts about the Planner's state, not wiring — and the SQLite file (`src/lib/db/plannerLock.ts`, one row via migration `0003_planner_lock.sql`) is already the one thing every module instance reads and writes correctly regardless of how many separate `better-sqlite3` connections open to it, the same way `planner_heartbeat` and `planner_run` already work (ADR 0005). `globalThis` remains the right tool only for state that can't be data — `modelCallRecorder` is a function reference, which SQLite cannot hold. The in-flight acquisition is a single `UPDATE planner_lock SET in_flight = 1 WHERE in_flight = 0` (checked via rows-changed), not a separate read then write, so the check-and-set stays atomic even across genuinely separate connections rather than relying on JS's single-threaded execution the way the old in-memory boolean implicitly did.

Because documentation alone proved insufficient to stop a second occurrence, we also added a lint rule (`no-restricted-syntax` in `eslint.config.mjs`) banning top-level mutable `let`/`var` in `src/lib/**/*.ts`, so the next instance of this mistake fails at PR time instead of surfacing only under a real `next build && node server.js` run. Turning it on immediately flagged two more pre-existing cases of the same shape — `dbInstance` (`src/lib/db/client.ts`) and `cachedEnv` (`src/lib/env.ts`) — neither confirmed broken nor confirmed safe; both are exempted with an `eslint-disable-next-line` pointing at #98, which tracks investigating and fixing them properly rather than mechanically copying this fix onto unverified cases. `planner.ts`'s `timer` is exempted too, but for the opposite reason: it's deliberately instance-local, since only the instrumentation module instance's own `setInterval` loop ever touches it.

## Consequences

- `runPlannerOnce()`'s in-flight check is now a database round-trip instead of a variable read, on a table with one row — negligible cost against a call that goes on to potentially call Ollama.
- ADR 0005's line describing the in-flight guard as "a single module-level boolean" is no longer accurate; see the note added there.
