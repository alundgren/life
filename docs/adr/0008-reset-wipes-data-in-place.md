# Reset wipes data in place with DELETE, rather than deleting the SQLite file, and refuses to run while the Planner is in flight

`POST /api/settings/reset` gives the user a "fresh reinstall" of their data without redeploying: every domain table is cleared and Mode/Time Budget are restored to their migration-seeded defaults (`work` / 180 / 600 minutes). A literal fresh install would delete the SQLite file itself and let `runMigrations` recreate it from scratch. We rejected that: the app holds one `better-sqlite3` singleton connection in WAL mode for its whole process lifetime (`src/lib/db/client.ts`), and Reset runs from a live web request on a running server — swapping the file out from under an open handle (or the `-wal`/`-shm` siblings) needs the connection closed and reopened, which in practice means restarting the process. In production that file also sits on Piploy's bind-mounted volume, making a mid-request restart riskier still. Instead, Reset runs one transaction that `DELETE`s every row from every domain table, in child-before-parent order, and re-`INSERT`s the two default rows, all against the existing connection. `schema_migrations` and the database file are never touched, so no migration replays and no restart is needed.

The visible cost is that Reset is a growing, hand-maintained list of tables (`src/lib/db/reset.ts`) rather than "delete the file" — a new table added by a future migration needs a matching line here, or it silently survives a reset.

We also decided Reset must refuse to run (409) while a Planner run is in flight, reusing the same `isPlannerRunInFlight()` guard added for the manual "run planner now" trigger. A Planner run reads its Task/Completion snapshot at the start and writes Corrections, Completion Digests, and Planned Activities as it goes; a Reset landing mid-run would delete rows the in-flight run still expects to reference, corrupting whatever it writes next rather than either finishing cleanly or failing atomically.
