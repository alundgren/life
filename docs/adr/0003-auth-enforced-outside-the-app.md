# Authentication lives entirely outside the app, in Cloudflare Access

The app is deployed to a Raspberry Pi 5 behind a Cloudflare Tunnel and needs to keep everyone but its single user out. It could have verified identity itself — Next.js middleware validating the `Cf-Access-Jwt-Assertion` header Access forwards to the origin, against the account's JWKS. Instead, no authentication code exists in the app at all. Access enforces the policy at Cloudflare's edge, and `cloudflared` on the Pi independently validates the Access JWT (`access.required` with the application's `audTag`) before proxying anything to the app. The app is never reachable except through that chain: the tunnel is outbound-only, and the app's port is not published beyond the Compose network.

We chose this because the system is single-user and has no concept of a user — there is no session, no ownership, no per-user data for a verified identity to unlock, so a validated JWT would tell the app something it has no use for. The allow-list is one email address held in an Access policy, which is deny-by-default; that policy *is* the user database, and keeping it in Cloudflare avoids adding a schema, a migration, and a login flow to serve one person. It also makes local development honest: `pnpm dev` skips authentication because there is nothing to skip, rather than because a flag mocks a user that production would have supplied. The cost is that all protection is configuration rather than code — it can't be covered by the test suite, and a misconfigured tunnel or a published container port silently removes it, so the deployment must keep the app unroutable by any path that doesn't traverse `cloudflared`. Should the app ever grow multi-user behaviour, the JWT is already at the origin and middleware can be added without changing the deployment.
