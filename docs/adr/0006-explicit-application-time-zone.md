# Calendar dates are derived in an explicit application timezone, not the host's

Calendar behavior — "today", the Monday a Weekly Plan starts on, a Scheduled Task's recurrence anchor, and Simulated Clock advancement — was derived from the host's ambient timezone. `Dockerfile.prod` sets no `TZ` and neither Compose file supplies one, so the production container runs in UTC and the calendar day flips at 01:00 or 02:00 Stockholm time depending on the season. The obvious fix is `TZ=Europe/Stockholm` in Compose; instead we require an `APP_TIME_ZONE` and derive every calendar value against that zone explicitly, leaving the host's zone irrelevant.

We chose the explicit route because `TZ=` makes the correct behavior invisible in the source and untestable: `pnpm test` would run under the developer's or CI's ambient zone, so the DST and midnight-boundary tests this change exists to add would assert whatever the host happened to be rather than what the app promises. An explicit zone gives the same answer on a laptop, on the Pi, and in CI. It must be a named IANA zone and never a fixed offset — Sweden's winter and summer offsets differ by an hour, and only the zone database knows when the switch happens.

The zone is a single deployment-wide setting rather than per-user: there is one user in one place, and relocating is accepted to mean editing configuration and regenerating plans. Two consequences follow. Application code now supplies `created_at`/`updated_at` on every insert unconditionally, retiring the `DEFAULT (datetime('now'))` fallback that left production's row stamps on SQLite's UTC clock in a second timestamp format — see ADR 0004, whose reasoning this extends from the Simulated Clock to every deployment. And the zone reaches the browser in the API response that already carries `today`, not as a `NEXT_PUBLIC_` variable, because `Dockerfile.prod` builds on the target device and `NEXT_PUBLIC_*` values are inlined at build time; sending it at runtime keeps the zone editable without a rebuild.
